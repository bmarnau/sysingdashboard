# L2 Cockpit P2b AVKK Server Read Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Den fehlenden AVKK-Server-Lesepfad für das Managementcockpit mit User-JWT und bestehender AVKK-Ableitung ergänzen.

**Architecture:** Ein neuer Supabase-Adapter liest ausschließlich über den vom Auth-Middleware-Kontext gelieferten User-Client; RLS bleibt die Sicherheitsgrenze. Der Adapter ordnet Subjects nur über `avkk_subject.systemhouse_id` und `customer_id` zu, baut mit `buildRows` die bestehenden AVKK-Zeilen und ermittelt mit `buildManagementSummary` die hohen/kritischen Signale je Kunde. Der bestehende Cockpit-Composer filtert zusätzlich auf den von `listMyCustomers` bestätigten Kundenkreis.

**Tech Stack:** TypeScript, TanStack Start Server Functions, Supabase JS/User-JWT, Vitest.

**Spec:** `docs/L2-COCKPIT-SCHNITT-KONZEPT.md` §11 und `docs/BSF-07-MANAGEMENT-COCKPIT-DESIGN.md` §§3, 4, 7, 8, 13, 14.

## Global Constraints

- Branch `feat/l2-cockpit-p2b` basiert exakt auf `feat/l2-cockpit-p2@1009887`.
- Keine Service Role, keine Schreiboperation, keine Migration, Tabelle, Policy, Rolle oder Permission.
- Keine Beträge, keine Personenwertung und keine zweite AVKK-Fachlogik.
- Keine Änderungen an `main` oder `lovable-sync-*`; Draft-PR gegen `main`, Merge nur durch den Nutzer.

## Review Focus

- RLS-gelesene Zeilen eines fremden Customers/Systemhauses dürfen nach der serverseitigen Kundenschnittmenge nicht im Ergebnis erscheinen.
- Fehler einer einzelnen AVKK-Abfrage müssen als `UNAVAILABLE` ohne Rohfehler erscheinen.
- Leere AVKK-Daten müssen `EMPTY`, nicht `UNAVAILABLE` und nicht künstlich `0` bedeuten.
- Schweregrad-Ränge müssen aus dem vorhandenen Katalog kommen; `HIGH_SEVERITY_RANK`/`CRITICAL_SEVERITY_RANK` bleiben Source of Truth.
- Der Adapter darf ausschließlich SELECT-artige Supabase-Aufrufe enthalten.
